# 处置规则

读取 `findings.md`，逐项判断是否纳入本次改动。判断目标是在可靠修复当前问题和避免引入不必要的回归风险之间取得平衡。每项只能标记为一个级别：必修、应修、缓修、不修。

## 必修

满足任一条件，标记为必修：

1. 影响正确性
   - 当前缺陷仍可能复现。
   - 新增逻辑存在明确的边界条件错误或行为偏差。
   - 涉及核心业务语义（如数据一致性、权限校验、安全策略、状态流转、关键计算）可能出错。

2. 误导故障排查
   - 日志、监控指标或追踪信息与代码实际执行路径不一致。
   - 错误日志级别滥用，例如把预期内的降级逻辑标记为 `ERROR`，或把严重故障降级为 `DEBUG`。
   - 代码注释或接口文档描述已过时，与新实现矛盾。

3. 存在冗余或废弃逻辑
   - 存在仅服务于已删除或废弃实现的辅助函数、条件分支或兜底策略。
   - 保留这些代码会诱导后续维护者误用或沿用错误模式。
   - 删除后不影响现有功能，且能显著提升代码可读性。

4. 破坏核心关注点的内聚性
   - 本次改动引入了核心模块或接口，但实现逻辑仍分散在多处。
   - 通过少量调整（如移动位置、提取方法）即可收敛相关逻辑，显著降低后续维护成本，且不扩大行为风险。
   - 重构范围不大（例如仅涉及单个文件或少数强相关文件，整体改动约数百行以内），行为边界清晰，测试或人工验证成本可控时，不得仅因属于重构而缓修。

5. 引入无关的行为偏移
   - 改动中混入了与本次目标无关的文案、样式、接口字段、缓存策略或路由变动。
   - 这些变动改变了旧功能的可见行为，不处理会增加审查复杂度和线上回溯难度。

6. 文件规模已明显影响可维护性
   - 单个文件超过约 500 行，且本次建议能通过小范围拆分、提取或收敛逻辑降低理解成本。
   - 拆分后不改变对外行为，不引入新的跨模块依赖，且审查成本可控。

7. 本次变更需要局部重构以保持内聚和可验证性
   - 本次新增或修改的同一业务规则分散在多个位置；不收敛会形成重复逻辑、行为分叉或状态不一致。
   - 不进行提取、移动或收敛，会使关键路径难以测试、审查、排障或明确职责边界。
   - 重构仅触及本次改动路径及其直接依赖，公开接口和业务可见行为保持不变，或行为变化已明确确认。
   - 改动范围、影响边界和验证方式清晰，可通过已有测试、少量新增测试或明确的人工验证独立确认。

## 应修

满足任一条件，标记为应修（非阻塞，但收益明显）：

1. 低成本、高确定性的优化
   - 例如补充测试清理逻辑（`try-finally`）、调整局部变量命名以提升可读性、补充简短注释说明设计意图。

2. 增强关键路径的测试覆盖
   - 本次改动引入了新逻辑分支，现有测试未覆盖。
   - 新增测试用例成本低，能锁定核心业务语义，防止未来回归。

3. 有效预防同类问题复发
   - 该问题属于常见的错误模式。
   - 通过补充单元测试或增加防御性断言，能以较低代价阻断高频复发路径。

## 缓修

满足任一条件，标记为缓修：

1. 与本次变更弱关联的纯代码风格或审美优化
   - 例如重命名现有变量或函数（不影响理解）、优化类型定义（无实际类型风险）、调整代码格式。
   - 重构现有逻辑结构（如抽取复杂工具类），但不能改善本次变更的正确性、可测试性、职责边界或重复逻辑，收益主要面向未来假设。
   - 不得仅因建议被标记为重构而缓修。若重构直接服务于本次变更的规则收敛、风险控制或验证，应按必修或应修评估。

2. 改动范围过大，放大风险
   - 涉及多个文件的大规模重构、模块迁移或测试架构调整。
   - 改动方向虽正确，但并非当前问题的必要条件，会显著增加审查成本。
   - 若重构仅涉及数百行以内、文件数量少、目标清晰且能独立验证，通常不应归入改动范围过大。

3. 应对未来潜在风险
   - 问题仅在特定未来场景（如高并发、扩展新类型）下才可能触发，当前生产环境输入完全受控。
   - 优化建议可记录为技术债务，不应混入本次改动。

4. 需要外部业务方或产品经理确认
   - 涉及用户体验、业务流程或文案变动，AI 不应擅自决定业务规则。
   - 应以待确认项形式输出，由负责人决策。

## 不修

满足任一条件，标记为不修：

1. 技术方案本质错误
   - 例如试图用应用层复杂逻辑替代数据库原生约束，或用分布式锁解决原本由唯一索引保证的数据一致性问题。
   - 为低频边缘场景引入高复杂度、高运维成本的基础设施。

2. 降低系统可观测性
   - 吞掉异常堆栈，将关键错误降级为静默失败。
   - 删除或弱化关键路径上的日志、追踪信息。

3. 破坏既有架构约定
   - 绕过统一的鉴权、日志、配置或数据访问层。
   - 在非业务层硬编码核心业务规则。
   - 将外部系统 ID 直接作为本地业务主键使用，绕开数据映射层。

## 判断顺序

按以下顺序权衡：

1. 本次改动是否完整且正确？
2. 是否引入了与改动目标无关的行为变化？
3. 是否会让故障排查变得困难？
4. 是否能通过局部重构提升本次关键路径的内聚性、可测试性或规则一致性？
5. 该改动的行为边界和验证方式是否清晰、可独立确认？
6. 改动集是否过大、过于分散，难以审查？

原则：不要因为能优化就默认修改，也不要仅因属于重构就默认缓修。只有收益明确、风险可控，且直接保障当前改动的正确性、可验证性、内聚性或后续维护一致性时，才纳入本次范围。

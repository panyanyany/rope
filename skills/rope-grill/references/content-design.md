# 中文文档写作规则

本规则用于需求澄清、计划、执行记录和长期文档。目标是让读者找到所需信息，理解要求，并完成下一步操作。

## 先说明读者要完成的任务

写作前明确读者、任务和完成条件。开头先写结论或下一步操作，再补充原因、限制和背景。

安装说明先给安装步骤。决策记录先说明决定。验证记录先说明结果及证据。历史背景放在当前操作说明之后，并明确其适用状态。

## 用标题和步骤组织内容

标题说明本节提供什么信息，例如“安装技能”或“检查返回证据”。避免只有“简介”“其他”这类无法帮助定位的标题。

有先后顺序的操作使用编号列表。并列条件使用项目列表。比较方案、字段或状态时使用表格。每段围绕一个主题展开。

保留必要的前置条件、失败处理和完成条件。不能为了缩短文档而删除这些信息。

## 写清执行者、动作和结果

优先使用主动表达。多人或多个代理协作时，明确谁执行动作。

一句话通常只给一项指令。连续动作拆成步骤；必须同时执行的动作可以写在同一句中。条件会影响操作时，先写条件，再写操作。

使用完整、直接的中文。可以省略已经明确的共同主语，但不能省略会影响责任、范围或先后顺序的信息。不要用斜线、加号或箭头串起需要解释的逻辑。

| 含糊表达 | 清晰表达 |
| --- | --- |
| 缺证据退回补对应项 | 如果返回结果缺少证据，父编排器应退回对应证据项，要求叶子工作者补齐。 |
| 新脑子铁律 | 每个切片必须能在一个全新上下文窗口内完成。 |
| 薄文书门 | 收尾前检查审查记录、E2E 结果和工作树状态。 |

## 同一概念使用同一术语

沿用项目术语表。技术术语首次出现时说明含义，后文保持一致。不要为避免重复而替换成含义不明的近义词或比喻。

面向用户时，用可观察行为解释内部术语。例如，把 Failure visibility 解释为“失败时，用户在哪里看到什么错误”。面向执行代理时，保留精确字段名，并用中文说明要求。

删除口号、夸张、无依据的评价和只对作者有意义的简称。把“更稳”“更好”等判断改成具体条件或结果。

## 区分要求、建议和选择

- 用“必须”说明强制要求。
- 用“不得”说明禁止事项。
- 用“建议”说明推荐做法，并写明适用原因。
- 用“可以”说明可选做法，并说明会影响结果的条件。

编辑时保留原规则的强度。不得把强制要求改成建议，也不得借文字整理增加审批、验收或执行要求。

## 保留协议和兼容入口

保留命令、路径、字段名、枚举值、代码标识和必要的原始输出。模板的说明和填写提示使用中文；自动化读取的名称保持原样。

修改标题时保留已有锚点。移动规则后修复引用，并让读者能从当前入口找到有效规则。链接文字应说明目标内容，避免“点击这里”。

区分 shell 命令与技能调用。只有 shell 命令放入 `bash` 代码块；技能调用说明应写清需要向代理发出的指令。

## 记录事实和证据

结论应能追溯到来源。区分已验证事实、假设、用户决定和待解决问题。未执行的验证不能写成通过。

保留历史决策的状态、范围、原因和取代关系。历史记录中的原话或原始输出可以保留，但不能让它们成为当前指令。

## 提交前检查

1. 开头是否帮助读者完成当前任务？
2. 每个操作是否写清执行者、条件和可观察结果？
3. 同一概念是否使用同一术语？
4. 是否保留全部有效约束、协议名称、命令和锚点？
5. 读者能否找到失败处理、完成条件和证据？
6. 删除一句话后，读者是否会失去必要信息？如果不会，考虑删除。

本规则结合 [GOV.UK 内容结构指南](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/writing-guidelines/clear-structure/)和[清晰语言指南](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/writing-guidelines/clear-language/)，采用任务优先、信息前置、明确标题和主动表达。

[ASD-STE100 官方说明](https://asd-ste100.org/STE_faq.html)支持将短句、单一主题和主动表达等原则用于其他写作场景；[第 9 版规则 5.2](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf)要求通常每句只写一项指令，并明确操作顺序。本规则借鉴这些原则，不将英文词典或词数限制换算成中文字数，也不声称中文文档严格符合 STE。
